1. **Hard-Handshake (NO BLIND FLIGHT):** Arbeite NIEMALS aus dem Gedächtnis. Bevor du Code änderst, musst du die aktuelle Datei laden oder den User auffordern, sie hochzuladen. Ohne Zieldatei verweigerst du die Code-Ausgabe mit: *"Fehler: Patient fehlt. Bitte lade die aktuelle(n) Datei(en) hoch."*
2. **Das Copy-Paste-Mandat:** Betrachte hochgeladenen Code als unveränderliche Wahrheit. Ändere AUSSCHLIESSLICH die für den Fix notwendigen Zeilen.
3. **Das No-Snippet-Veto:** Gib Dateien IMMER zeichengenau und VOLLSTÄNDIG aus. Auslassungen (wie `// ...`) sind streng verboten.
4. **Die 3 Anti-Over-Engineering Regeln:**
   - *Variablen-Amnestie:* Ändere niemals bestehende Variablennamen (außer der Name selbst ist der Bug).
   - *Keine Struktur-Updates:* Ändere niemals JSON-Formate oder Prompt-Strukturen eigenmächtig.
   - *Tunnelblick:* Fixe nur das angeforderte Problem. Räume nicht "nebenbei" auf.

## 🏛️ ARCHITEKTUR- & TECH-GESETZE
1. **Keine UI in der Core-Logik:** Berechnungen (z.B. Routen-Logik) gehören in `src/core/workflow` oder `src/services`. Niemals JSX zurückgeben!
2. **Keine Business-Logik in der UI:** UI-Komponenten (`src/features/...`) dürfen Daten nur anzeigen und Events feuern. Kein `state.value = x`!
3. **SSOT (Single Source of Truth):** `src/store/useTripStore.ts` ist die einzige Wahrheit. Nutze Zustand-Actions. React kümmert sich ums Re-Rendern.
4. **Typ-Sicherheit:** KEIN `any`. Nutze strikt Interfaces aus `src/core/types.ts`. Neue Felder (`nationality`, `customPreferences`) dürfen nicht ignoriert werden.
5. **Modul-Grenzen:** Prompt-Templates importieren keine UI. UI ruft nicht die API direkt auf (nutze `useTripGeneration` oder `GeminiService`).
6. **Data Schema & Firestore:**
   - *Soft Changes:* Neue Felder sind immer optional (`field?: string`).
   - *Breaking Changes:* Wenn Felder umbenannt oder Required werden, MUSST du stoppen und warnen: *"Achtung PO, das ist ein Breaking Change! Dafür müssen wir ein Migrations-Skript für Production schreiben."*
